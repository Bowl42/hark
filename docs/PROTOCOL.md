# hark streaming recognition protocol

hark exposes this single protocol downstream, regardless of which ASR is connected upstream. Design goals:

- **Native support for corrections**: upstream rewrites text it has already output ("今天天汽" → "今天天气", fixing a misrecognized character). The protocol uses ops to say exactly "in which segment, replace characters i through j with what", so the bytes sent depend only on the size of the change
- **Explicit about which text will never change**: content before the `commit` watermark is never modified, so downstream can safely hand it off (write it to a database, send it to an LLM, execute a command)
- **Multiple tracks**: one recognition can produce several independent results at once: comparing multiple engines, or recognizing each channel separately
- **Multiple sequential recognitions on one connection**, saving a new connection each time

Go clients can use the [`api`](../api) package directly: the message structs, plus `api.Doc` (one per track), which merges updates according to this protocol.

## Connection

```
GET /v1/stream          (WebSocket)
Authorization: Bearer <token>        # or ?token=<token>; may be omitted if the server has no tokens configured
```

If the token is invalid, the handshake fails with HTTP 401.

## Session flow

```
Client                                       Server
  │── start ─────────────────────────────────▶│
  │◀──────────────────────── started / rejected│
  │── [binary PCM] ──────────────────────────▶│
  │◀────────────────────────── update(track) * │   pushed by each track at any time
  │── finish ────────────────────────────────▶│
  │◀────────────────────────── update(track) * │
  │◀─────────────────────── track_end × tracks│   exactly one per track
  │◀──────────────────────────────────── end  │
  │── start ─────────────────────────────────▶│   the same connection can start the next one
```

Connection states: idle → recognizing → finalizing (finish sent) → idle.

- The next `start` may only be sent after `end` is received; sending `start` while recognizing is a protocol error
- For every accepted start (one that received `started`): as long as the connection is still writable, each track receives exactly one `track_end`, followed by exactly one `end`. If the connection drops, the client may never learn the final state
- If every track ends early (for example, all of them fail), the session ends immediately with `end`, without waiting for the client's finish
- A rejected start receives `rejected`; the connection stays idle and start can be sent again

## Tracks

A recognition contains 1 to 8 **tracks**. Each track is an independent result with its own segments, revision number, `stable` and `commit`. A track's number is its index in the `start.tracks` array; tracks are never added, reordered or reused during a session.

Each track sends the audio of one channel to one engine. Several engines on the same channel give **multi-engine comparison**; one track per channel gives **per-channel recognition**.

- **An error on one track doesn't affect the others.** If an engine fails to open, fails during recognition, or gets stuck and stops consuming audio, only its own track ends
- **A speaker is not a track; it is a segment attribute** (`segment.speaker`). When several people speak on one channel, the result is still one conversation in time order; when the engine reassigns a speaker, that segment's label changes, expressed as an ordinary correction
- Speaker labels are scoped to their track: the same label on different tracks (e.g. two engines) does not mean the same person. Segments are also not guaranteed to correspond one-to-one across engines; compare them by `audio_range`

## Client → server

### start

```json
{
  "type": "start",
  "request_id": "r1",
  "audio": { "encoding": "pcm_s16le", "sample_rate": 16000, "channels": 2 },
  "tracks": [
    { "engine": "sensevoice", "channel": 0 },
    { "engine": "whisper", "channel": 0 },
    { "engine": "sensevoice", "channel": 1 }
  ],
  "output": { "mode": "delta" },
  "commit": { "policy": "strict" }
}
```

In this example, a phone call has the agent on the left channel and the customer on the right. Tracks 0 and 1 recognize the agent with two engines for comparison; track 2 recognizes the customer.

| Field | Required | Description |
|---|---|---|
| `request_id` | yes | Generated by the client, used to match `started` / `rejected` |
| `audio` | yes | `pcm_s16le` / `16000` / 1 to 8 channels |
| `tracks` | no | Track list, 1 to 8 tracks. **If omitted, one engine track per channel**, using `engine` or the server default |
| `engine` | no | Default engine for engine tracks. See `GET /v1/engines` for available engines |
| `options` | no | Default parameters for engine tracks, passed through to the engine as is (e.g. hotwords) |
| `user` | no | User name (`[a-z0-9._-]`, 1 to 64 characters, case-insensitive); enables this user's [personal vocabulary](#personal-vocabulary). `rejected` if the server doesn't have personal vocabulary enabled |
| `output.mode` | no | `delta` (default): push intermediate results; `final`: no intermediate results, only the final result in `track_end.snapshot` |
| `commit` | no | See [commit policy](#commit-policy). Defaults to `{"policy":"strict"}`; applies to all tracks, each advancing independently |

**Track** `{"engine": ..., "channel": ..., "options": ...}`; all three fields may be omitted

| Field | Description |
|---|---|
| `engine` | Engine name; if omitted, uses `start.engine` or the server default |
| `channel` | Channel number, starting at 0, default 0 |
| `options` | Engine parameters for this track. If omitted, inherits `start.options`; `{}` means no parameters (no merging) |

All validation happens before any engine is opened: unknown fields (including nested ones), unsupported values, unknown engines and out-of-range channels are all `rejected`, never silently ignored.

### Audio (binary messages)

Interleaved PCM (`L R L R ...`) in the format given by `start.audio`; the length must be a multiple of `2 × channels` bytes. 20 to 200 ms per message is recommended; sending at real-time speed is fine.

Each track buffers a limited amount of audio. When the buffer is full, the server stops reading, applying TCP backpressure to the client, so pushing faster than real time is naturally throttled; the slowest track sets the overall pace. If a track's buffer stays full without being consumed for 10 seconds, its engine is stuck, and **only that track ends** (`engine_error`); the other tracks continue.

### finish

```json
{ "type": "finish" }
```

End of audio. Sending it again has no effect. Sending audio after finish is a protocol error.

### cancel

```json
{ "type": "cancel" }
```

Abandon the current session: every track that hasn't ended receives a `track_end` with `reason: cancelled`, followed by an `end` with `reason: cancelled`. Ignored when there is no active session.

## Server → client

### started

```json
{
  "type": "started",
  "request_id": "r1",
  "session_id": "9f1c...",
  "audio": { "encoding": "pcm_s16le", "sample_rate": 16000, "channels": 2 },
  "output": { "mode": "delta" },
  "commit": { "policy": "strict" },
  "tracks": [
    { "track": 0, "engine": "sensevoice", "channel": 0 },
    { "track": 1, "engine": "whisper", "channel": 0 },
    { "track": 2, "engine": "sensevoice", "channel": 1 }
  ]
}
```

Echoes the parameters and track layout actually in effect (omitted defaults are filled in). `started` means the track layout was accepted; it doesn't guarantee that every track connects upstream successfully: a track that fails to connect receives a `track_end` with an error.

### rejected

```json
{ "type": "rejected", "request_id": "r1", "error": { "code": "unknown_engine", "message": "..." } }
```

### update (core)

```json
{"type":"update","track":0,"rev":12,"ops":[{"retain":1},{"update":{"text":[{"retain":3},{"delete":1},{"insert":"气很好。"}]}},{"insert":[{"text":"我们"}]}],"stable":1,"commit":0}
```

Each track's result consists of **segments**, usually one sentence each. **The full text is the segments' `text` concatenated directly.** Spaces, punctuation and newlines are all inside `text`; the client doesn't need to, and shouldn't, add spaces itself.

| Field | Description |
|---|---|
| `track` | Track number. All the fields below apply to this track only |
| `rev` | Revision number; starts at 1 for each track and increases by 1 with every update. **A received rev must equal that track's previous rev plus 1**; otherwise the implementation is broken and the client should disconnect |
| `ops` | Optional. Omitted when neither text nor segments changed and only the watermarks moved |
| `stable` | Upstream considers the first `stable` segments final. Only a hint: it can move back, but never below `commit` |
| `commit` | The first `commit` segments **will never change again**: text, segment boundaries, speaker and timestamps all stay fixed. Only ever increases |

Constraint: `commit <= stable <= number of segments` (after applying ops). Both watermarks are **segment counts**, not indexes.

#### ops

The format borrows the operation sequences of OT (Operational Transformation); since the server is the only writer and messages are ordered, the "transform" part of OT isn't needed. There are two levels with the same rules:

- **Segment level**: the cursor starts at segment 0 and the ops run in order over the **old segment list**; any old segments left after the last op are kept as is
- **Within a segment**: the `text` inside `update` is also an op sequence; the cursor starts at character 0 of that segment's text, and remaining characters are kept as is

| Segment-level op | Meaning |
|---|---|
| `{"retain": n}` | Keep the next n old segments unchanged; cursor advances n |
| `{"delete": n}` | Delete the next n old segments; cursor advances n |
| `{"insert": [segment, ...]}` | Insert these new segments at the cursor; cursor doesn't move |
| `{"update": {...}}` | Modify the next old segment; cursor advances 1, see below |

Contents of `update`:

```json
{"update": {"text": [{"retain": 2}, {"insert": "下午"}], "speaker": "S1", "audio_range": {"start_sample": 0, "end_sample": 35200}}}
```

- `text`: optional; omitted means the text is unchanged. Ops within the segment: `{"retain": n}` keeps n characters, `{"delete": n}` deletes n characters, `{"insert": "..."}` inserts text
- `speaker`, `audio_range`: the segment's **complete** metadata after the change, replacing the old values entirely. A field that isn't given is gone (for example, after a segment is split its time range is no longer accurate, so `audio_range` is left out)

Examples (old state `["今天下午三点在二号会议室。", "天气"]`, "3 pm today in meeting room 2." / "weather"):

| New state | ops |
|---|---|
| `["今天下午三点在二号会议室开会。", "天气"]` | `[{"update":{"text":[{"retain":12},{"insert":"开会"}]}}]` |
| `["今天下午3点在2号会议室。", "天气"]` | `[{"update":{"text":[{"retain":4},{"delete":1},{"insert":"3"},{"retain":2},{"delete":1},{"insert":"2"}]}}]` |
| `["今天下午三点在二号会议室。", "天气很好"]` | `[{"retain":1},{"update":{"text":[{"retain":2},{"insert":"很好"}]}}]` |
| `["今天下午三点在二号会议室。", "天气", "我们"]` | `[{"retain":2},{"insert":[{"text":"我们"}]}]` |
| `["今天下午三点在二号会议室。天气"]` | `[{"update":{"text":[{"retain":13},{"insert":"天气"}]}},{"delete":1}]` |

Rules (the same at both levels):

1. Each op is an object with **exactly one field**; `retain` and `delete` are integers greater than 0, and `insert` must not be empty
2. `retain`, `delete` and `update` must not run past the end; `text` must not be an empty array
3. At segment level, the first op that isn't `retain` must be at a position (old segment index) no less than the current `commit`
4. Any violation means the implementation is broken; the client should disconnect

The ops the server sends are canonical: no adjacent ops of the same kind (except adjacent `update`s), no trailing `retain`, no `update` for an unchanged segment, and within a segment each change is `delete` first, then `insert`.
The segment mapping and the in-segment diff are computed heuristically by the server: the result is always correct (applying it yields the new state), but it isn't guaranteed to reproduce how upstream "really" changed the text, nor to be minimal.

**Characters are counted in Unicode code points** (strictly, Unicode scalar values), not bytes and not UTF-16 units. In JavaScript, split by code point with something like `Array.from(str)`.

Go clients can use `api.Doc.Apply` directly; it includes all of the validation above.

To tell "appended text" apart from "changed text", or when you can only backspace and retype (a typewriter effect), compare the **full text** before and after applying, not just the ops: merging segments produces a `delete` even though the full text is unchanged.

#### Segment

```json
{ "text": "我要退货。", "speaker": "S1", "audio_range": { "start_sample": 0, "end_sample": 35200 } }
```

| Field | Description |
|---|---|
| `text` | Text |
| `speaker` | Optional. Speaker label, scoped to this track. A segment has only one speaker |
| `audio_range` | Optional. The segment's position in the input audio: a half-open interval in samples (at 16 kHz, 1 ms = 16, counted per channel), measured from the session's first sample |

Optional fields appear only when the engine provides them.

### track_end

```json
{ "type": "track_end", "track": 0, "reason": "done", "dropped_revisions": 0 }
```

| Field | Description |
|---|---|
| `reason` | `done` ended normally; `error` failed; `timeout` timed out; `cancelled` cancelled by the client |
| `error` | Error details when not `done`: `{code, message, retryable?}` |
| `dropped_revisions` | Number of upstream snapshots partly or wholly dropped due to freeze conflicts; see the freeze policy |
| `snapshot` | `final` mode only: `{segments, stable, commit}` |

- `done`: in delta mode, an update with the track's final state has always been sent before track_end, with `commit = stable = number of segments`, so nothing will change again. Exception: if the recognition result is empty, no update is sent and the state stays at the initial `rev=0, stable=0, commit=0`
- Other reasons: remaining content is **not** committed automatically; the state of the last update is the final state. In `final` mode the snapshot is a partial result

### end

```json
{ "type": "end", "reason": "done", "status": "partial" }
```

Sent after all `track_end`s. The two fields answer two different questions:

| Field | Answers | Values |
|---|---|---|
| `reason` | Why the session stopped | `done` wrapped up normally; `cancelled` cancelled by the client; `timeout` exceeded the maximum session duration; `error` internal server error |
| `status` | Whether the result is complete | `complete` all tracks done; `partial` some tracks done; `failed` no track done (doesn't mean there is no partial text) |

For example, when comparing engines and one fails while the other succeeds: `reason: done, status: partial`. The client only needs to retry what the failed track was for, not the whole session.

### error (connection level)

```json
{ "type": "error", "error": { "code": "protocol_error", "message": "start while a session is active" } }
```

When the client violates the protocol (invalid JSON, unknown message type, audio before start, start while recognizing, audio length not aligned to the channel count, etc.), the server sends this message and closes the connection. Any session in progress is abandoned, with no track_end / end.

### Error codes

| code | Appears in | Description |
|---|---|---|
| `bad_request` | rejected | Invalid start parameters |
| `unsupported_audio` | rejected | Unsupported audio format |
| `unknown_engine` | rejected | Engine doesn't exist |
| `engine_error` | track_end | Engine failed to connect, failed during recognition, or got stuck; usually `retryable` |
| `timeout` | track_end / end | Exceeded the maximum session duration, or finalizing after finish timed out |
| `internal` | track_end / end | Internal server error |
| `shutting_down` | rejected / track_end / end | The server is shutting down; `retryable`. While shutting down, no new sessions are accepted; sessions in progress get about 5 seconds to finish speaking and send finish, and those still running after that are aborted with this code (committed text remains valid). The connection is then closed with 1001 (going away) |
| `protocol_error` | error | The client violated the protocol |

`retryable` means the same request may succeed if made again on another connection (or later, or on another instance); it doesn't mean the original session can be resumed,
and tracks that already succeeded don't need to be redone.

## commit policy

commit guarantees that the result won't change again; it doesn't guarantee the recognition is correct.

### strict (default)

All content is committed at once, only when the track ends normally (`done`); while in progress, `commit` stays at 0. Downstream consumers that want to use text while the user is speaking should consume by `stable` in a revocable way (display first, submit after commit).

### freeze

```json
{ "commit": { "policy": "freeze", "after_ms": 1500 } }
```

Once a segment is in `stable`, if it and everything before it (text and metadata) stay unchanged for `after_ms`, **the gateway freezes it** (commit advances). Suited to downstream consumers that need results handed over while the user speaks.

Freezing is the gateway's promise, not an upstream guarantee. Later upstream changes to frozen content are ignored, and the gateway tries to locate the new content using these methods, most reliable first:

1. The frozen text is unchanged and upstream only re-segmented: split at the freeze boundary, **losing nothing**. Upstream changes to the speaker or timestamps of frozen segments are likewise ignored, and `dropped_revisions` increases by 1
2. The frozen text was rewritten (e.g. number normalization), but the engine provides `audio_range`: segments starting no earlier than the end of the frozen content are new content and go in as usual; segments straddling the freeze boundary are dropped (any new content in them is lost), and `dropped_revisions` increases by 1
3. The frozen text was rewritten and there is no timing information: **the new content can't be located reliably, so the whole snapshot is dropped**, and `dropped_revisions` increases by 1. If upstream keeps this rewrite from then on, no new content on that track gets through until it ends

The gateway never guesses boundaries by character length: number normalization and similar rewrites change the text length, and aligning by length would duplicate or lose content.

freeze trades a little accuracy for earlier delivery and **works best with engines that provide segment timestamps**; `dropped_revisions` lets you monitor its cost.

## Editing while speaking

Before recognition ends, the user may edit text in the input box. **This is handled entirely on the client; the protocol needs no cooperation**, and it works with every engine:

- The client keeps two copies: a **recognition mirror** (only updates are applied, by rev, and it is never edited) and a **user document** (shown to the user, who can edit it). Don't edit the recognition mirror directly, or the coordinates of all later ops will be wrong
- Track the **ranges the user actually edited**. For each update, apply the recognizer's change to the mirror, then carry the user's edits over:
  - The recognizer's change doesn't overlap the user's edit: keep both. The recognizer keeps correcting text the user didn't touch, and newly spoken text is appended as usual
  - The recognizer changed the text to the same thing the user wrote: that edit simply disappears, with no duplicated text
  - Overlap: **the user's text stays**, marked as a conflict, with the recognizer's version shown as a suggestion that the user can accept or ignore. When the recognizer's change doesn't line up with the boundaries of the user's edit, the conflict conservatively widens to cover the whole change, and shrinks back once the recognition result lines up again
- Don't merge mechanically with OT transforms: they only guarantee both sides converge, not that the result makes sense; whole-sentence re-recognition would produce duplicated and out-of-order text

Go clients can use the [`draft`](../draft/draft.go) package directly. When typing with an input method (IME), hold updates during composition and merge them after the text is committed, so the IME isn't interrupted.

## Personal vocabulary

For a word the recognizer keeps getting wrong (say, it always hears "hark" as 哈克), once the user has corrected it to the same word repeatedly (conditions below), hark replaces it automatically. **The client doesn't need to diff or store anything**:

1. Include `"user": "alice"` in `start`
2. After an **engine track** ends and the user has finished editing, send back the recognition result and the user's corrected full text:

```
POST /v1/users/alice/corrections
{"id": "<session_id>:<track>", "before": "<full recognized text>", "after": "<full text as corrected by the user>"}

→ {"activated": [{"from":"哈克","to":"hark","state":"active",...}], "deactivated": [], "skipped": 0, "duplicate": false}
```

- For `before`, use the recognition result the client received (`Mirror()` of `draft.Draft`, or the full text of `api.Doc`); for `after`, use the text box contents. **Send it even if nothing was edited** (`before` = `after`): a word that appeared in the result and that the user didn't change is evidence that it shouldn't be replaced. Don't send while there are unresolved conflicts (conflict regions aren't evidence of corrections)
- `id` is used for deduplication (at most 128 bytes); reuse the same one when retrying. The last 512 submissions are remembered per user. If omitted, deduplication is by content
- When `activated` is non-empty, consider telling the user "Learned: 哈克 → hark" and offering undo (see DELETE below)

How the server learns:

- before and after are aligned by sentence, then by character, and only **word-level** replacements are learned (at most 16 characters per side). Sentences with changed punctuation, rewritten sentences, and whole English words added or removed are not learned
- Single-character changes include the neighboring characters (他们 → 她们, masculine to feminine "they", rather than 他 → 她), so single-character rules don't fire everywhere
- A rule becomes active only once it **has been corrected this way in at least two submissions**, and among the submissions the server has received, the word **was corrected at least 80% of the times it appeared** in the recognition result. For example, 明天 ("tomorrow") sometimes changed to 后天 ("the day after tomorrow") and sometimes left alone usually won't become active
- This is only statistics: it only counts transcripts submitted by the client after the candidate appeared, so it **can still learn wrong** (for example, correcting 明天 to 后天 twice in a row). The user undoes wrong rules, and the client should keep active entries visible and undoable at all times
- Once active, the recognition result is the replaced text directly. If the user changes "hark" back to 哈克, the rule is deactivated and won't be learned again automatically (while the rejection record is kept; see the limits below)

Replacement rules:

- Replacement happens as engine results enter hark, so `update` and `commit` (including the freeze timer) all see the replaced text. A snapshot of the vocabulary is taken when a session starts; words learned during a session take effect from the next session
- Replacement only happens within a segment, longest match first. English words must match whole words ("hack" doesn't match "hacker"), case-sensitively
- Known limitation: with the freeze policy, if the engine re-segments after freezing and splits a word across two segments, the replacement result changes, which may trigger freeze conflict handling (see above)

Management API:

| Endpoint | Purpose | Returns |
|---|---|---|
| `GET /v1/users/{user}/words` | List all entries: `active`, `candidate` (not enough evidence yet), `rejected` (undone) | `{"words": [entry, ...]}` |
| `POST /v1/users/{user}/words` `{"from","to"}` | Add manually; active immediately, replaces other active rules with the same `from`, and is never overridden by automatic learning | entry |
| `DELETE /v1/users/{user}/words?from=哈克[&to=hark]` | Undo (without `to`, undoes all entries for this word). Undone entries won't be learned again automatically; adding them manually restores them | `{"rejected": number of entries undone}` |

Entry: `{"from","to","state","source":"auto|manual","fixed":times corrected,"seen":times seen,"updated":"RFC 3339 time"}`.

- User names are `[a-z0-9._-]{1,64}`, case-insensitive
- Manual entries have 1 to 32 characters per side, no newlines or leading/trailing spaces, and the two sides must differ
- Limits: at most 1000 active rules per user (once full, manually adding a new `from` returns an error and automatic learning adds no more; replacing an already active `from` is unaffected) and 10000 entries; when entries are full, the oldest candidates and rejection records are evicted, and an evicted rejection record may be learned again automatically
- `before` and `after` in corrections are each at most 64 KB (65536 bytes); the whole request body is at most 256 KB
- Errors: `400` invalid parameters or active rules full, `401` bad token, `404` personal vocabulary not enabled (`data_dir` not set), `413` request too large, `500` storage error, `503` server shutting down; error messages are plain text

These endpoints use the same tokens as `/v1/stream`. For now (private network), **there is no per-user identity**: anyone who knows a user name can read and write that user's vocabulary.

## Other endpoints

- `GET /v1/engines` → `{"default":"sensevoice","engines":[{"name":"sensevoice","type":"sherpa"}, ...]}` (also requires a token)
- `GET /healthz` → `ok`

## Current limitations

- No tracks derived from another track's text (translation, rewriting)
- No native multi-channel engines: hark always splits channels and gives each track a mono engine
- No reconnection/resume, no Opus input, no word-level timestamps (only segment-level `audio_range`)
